# Warcraft Codex Workspace

Приватное веб-приложение для общения с разрешёнными задачами Codex.
Telegram используется только для входа; бот, Mini App и Bot API для работы
интерфейса не нужны. Интерфейс основан на [LuSeptem/codex-webui](https://github.com/LuSeptem/codex-webui):
[заимствованные компоненты и лицензия](web/UPSTREAM.md).

## Текущее состояние

Вход, права на задачи, общая история, вложения и одобрение работают на VM.
Проверены реальные доставка текста и файла в существующую задачу Codex и возврат
её ответа. История синхронизирована; интерфейс запоминает позицию чтения и
открывает конец при первом посещении задачи.

**Автономный CLI-обработчик подготовлен, но пока не включён.** Живой тест
`codex exec resume` продолжил существующую неактивную задачу с тем же UUID;
desktop увидел новый завершённый ход. Попытка продолжить занятую задачу
получила отказ `already has an active writer`. Это позволяет обойтись без
подключения второго клиента к stdio-транспорту desktop.
Передача модели, reasoning и исходных прав прошла живую проверку; полный путь
с сайта через `cli_worker.py` ещё проверяется. Запланированная задача Codex для polling не используется.
Отдельный Codex на VM в эту схему не входит.

## Как устроено

- Веб-приложение работает на отдельной VM в Yandex Cloud: React, Python API,
  SQLite и приватные вложения на диске. API Gateway предоставляет HTTPS и
  обращается к VM по внутренней сети.
- Telegram Login проверяется на сервере: OIDC — по RS256, issuer, audience,
  nonce и срокам; Login Widget — по HMAC-SHA256 с ключом конкретного бота,
  времени авторизации и защите от повторного использования подписанного ответа.
  При первом входе разрешённый username привязывается к числовому Telegram ID.
- Владелец видит каталог тредов выбранного проекта и выдаёт участникам доступ
  к конкретным тредам. Участники разрешённой задачи видят общую переписку и отправленные в неё вложения.
- Каждый запрос требует одобрения владельцем, включая запросы самого владельца.
  Одобрение фиксирует текст, тред и SHA-256 каждого вложения.
- Ноутбук получает одобренные запросы исходящими HTTPS-запросами. Передача
  существующей задаче выполняется инструментами приложения Codex. Входящие
  порты, VPN-тоннель и второй App Server не требуются.
- Веб-интерфейс показывает общую историю разрешённых задач. Сборщик передаёт
  только видимые сообщения пользователя и ассистента, без внутренних рассуждений
  и вывода инструментов. Доступ к истории проверяется при каждом запросе.

До четырёх файлов по 5 МБ на запрос; максимум 100 МБ вложений в облачном
mailbox. Запросы и файлы хранятся семь дней, одобрение действует сутки.
Файлы загружаются частями, проверяются по SHA-256 и не исполняются.
Сессия сайта живёт до восьми часов и сохраняется при обновлении страницы.
Случайный идентификатор хранится в Secure/HttpOnly cookie; сервер хранит только
его хеш. Запросы защищены проверкой Origin и CSRF-токеном, выход отзывает сессию.
Черновики остаются только в памяти вкладки. Для входа достаточно корневого URL
сайта: параметры вроде `v=widget-login` не нужны.

## Разработка и проверки

```sh
python3 -m venv .local/test-venv
.local/test-venv/bin/pip install -r server/requirements.txt httpx
.local/test-venv/bin/python -m unittest discover -v
npm ci --prefix web --ignore-scripts
npm --prefix web run build
cd web && npx playwright install chromium && npx playwright test
```

Браузерные тесты подменяют API только внутри тестового браузера. В сервере
нет тестового входа или режима обхода Telegram Login.

[Развёртывание VM и эксплуатация](docs/deployment.md).
[Архив локального прототипа](docs/legacy-local-prototype.md),
[архив Cloud Functions](docs/legacy-cloud-functions.md).
Прежние Telegram polling/webhook и тестовая heartbeat-автоматизация остаются
отдельными механизмами и не должны включаться для нового веб-приложения.

`.local/`, ключи, токены, очереди, вложения и сборки не коммитятся. Проект
не изменяет игровой launcher и не содержит учётные данные Codex.
