# Подготовка публичного релиза

Перед сменой видимости:

1. Проверить `main` и экспериментальную ветку, включая всю доступную Git-историю,
   а не только рабочие файлы. Автоматический поиск: Gitleaks 8.30.1,
   `gitleaks git --redact=100 --log-opts="--all"`. CI запускает тот же инструмент
   с проверенным SHA-256 бинарника. Не публиковать неретушированные отчёты.
   `.gitleaksignore` исключает только конкретную синтетическую строку старого теста.
   Сканер не доказывает отсутствие всех секретов или личных данных.
2. Пройти [установку с нуля](installation.md); не использовать готовую `.local`.
   Python-проверки: `CODEX_WORKSPACE_SOURCE="$PWD" python -m unittest discover -s tests -t . -q`.
   Проверить сборку wheel и установку вне checkout. Реальный cloud provisioning
   и iOS-проверка отдельно от локальных интеграционных тестов.
3. Проверить лицензии: MIT собственного кода в корне и исходное уведомление
   LuSeptem в `web/licenses`. Оба включаются в Python-пакет и серверный релиз.
4. При переключении на public включить Settings → Advanced Security → Private
   vulnerability reporting, затем проверить ссылку из [SECURITY.md](../SECURITY.md).
   [Инструкция GitHub](https://docs.github.com/en/code-security/how-tos/report-and-fix-vulnerabilities/configure-vulnerability-reporting/configure-for-a-repository).
   Сейчас наличие файла политики само по себе не включает приватную форму.
5. Проверить запуск CI и сделать Secret scan обязательной проверкой ветки.
   Ограничения оплаты/минут GitHub Actions нужно устранить в настройках аккаунта;
   локальные успешные тесты не означают, что Actions запустился.

Не включать состояние, recovery, клиентский ключ, служебные логи, private deployment
настройки, содержимое переписки или машинные отчёты. Перед публикацией вложений
релиза отдельно проверить их состав. Публичность исходников не делает работающий
сервер общедоступным и не означает независимый аудит безопасности.
