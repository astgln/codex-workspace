# Архитектура Codex Workspace

`main` предоставляет личный доступ к задачам существующей установки Codex.
Telegram используется только для входа. Единственный аккаунт задаётся
`OWNER_USERNAME`; после первого проверенного входа закрепляется числовой Telegram ID.
Смена username не передаёт доступ новому владельцу прежнего имени.

## Компоненты

| Компонент | Назначение |
| --- | --- |
| `web/` | React, TypeScript, Vite, Markdown/diff, PWA и Web Push |
| API Gateway | Публичный HTTPS, маршрутизация на VM |
| `server/` | FastAPI, cookie-сессии, файлы, история, push, SQLite |
| `cloud/` | Чистая логика входа, каталога, запросов и ответов; Cloud Functions не нужны |
| `cli_worker.py` | Исходящий polling, локальная очередь, запуск CLI и публикация результата |
| `history_watch.py` | История, текущая активность и недельная квота |

## От сообщения до ответа

1. Браузер подтверждает Telegram-вход на сервере и получает защищённую cookie.
2. Сервер проверяет числовой ID аккаунта и CSRF, сохраняет текст, целевую задачу,
   снимок вложений и ключ идемпотентности. Новый запрос имеет состояние `queued`.
3. Локальная служба забирает запрос с короткой арендой, записывает его в SQLite
   и подтверждает получение. Сервер переводит запрос в `delivered`.
4. Перед запуском служба перепроверяет доступность цели, срок и снимок запроса.
   Файлы проверяются по SHA-256. Права CLI берутся из сохранённого контекста задачи.
5. Намерение запуска сохраняется до `codex exec resume`. Ответ связывается
   с конкретным новым ходом, а не с последним сообщением в задаче.
6. Публикуются состояния `running`, затем `completed`, `failed` или `needs_input`.
   Браузер получает обновления опросом; push содержит название задачи и начало ответа.

При занятой desktop writer lock запрос остаётся в ожидании. При неопределённом
результате отправки автоматического повторного запуска нет: необходима сверка хода.
CLI не получает инструменты `codex_app` открытого desktop-приложения.

## История и каталог

История синхронизируется независимо от выполнения: только пользовательский текст
и публичные commentary/final ответы. Внутренние рассуждения и вывод инструментов
не публикуются. Чтение журналов возобновляется с проверенных смещений.
Каталог автоматически обновляется read-only адаптером `desktop_catalog.py`
из явных назначений проектов в локальном состоянии desktop. При неизвестном
формате адаптер сохраняет последний корректный снимок и сообщает об ошибке.
Работающие задачи определяются по текущему ходу и writer lock.

## Хранение и ветки

SQLite schema 4 содержит идентичность, каталог, запросы, файлы, события, сессии
и push-подписки. Переход со старых схем транзакционный, с проверкой соответствия
данных, частной резервной копией и репетицией восстановления. История и файлы
сохраняются. Запросы, ранее не готовые к исполнению, автоматически не запускаются.
Импорт старых форматов изолирован в `server/schema_legacy.py`.

Ветки используют отдельные checkout и базы. Старую версию нельзя направлять
на schema 4. Действующий сайт Yandex Cloud развёртывается из
`experimental/multi-user`; `main` туда не публикуется.
