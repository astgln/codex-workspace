# Архитектура Codex Workspace

`main` предоставляет личный доступ к существующим задачам Codex. Telegram
используется только для входа; после первого входа закрепляется числовой ID.
Вход не выдаёт ключи шифрования: браузер отдельно привязывается к доверенному
устройству. Протокол и ограничения описаны в [e2ee.md](e2ee.md).

## Компоненты

| Каталог | Ответственность |
| --- | --- |
| `web/src/app` | Сборка приложения и маршрутизация состояния |
| `web/src/features` | Вход, проекты, чат, шифрование, уведомления, диагностика |
| `web/src/shared` | Типы, HTTP-клиент, общие компоненты и статусы запросов |
| `src/codex_workspace/agent` | Исходящие сборщики, локальная очередь и зашифрованная синхронизация |
| `src/codex_workspace/codex` | Чтение каталога/журналов и запуск CLI в существующей задаче |
| `src/codex_workspace/crypto` | Криптографические примитивы и формат конверта |
| `src/codex_workspace/devices` | Локальное хранилище ключей, доверие, привязка устройств |
| `src/codex_workspace/relay` | FastAPI, cookie-сессии, SQLite и доставка зашифрованных записей |
| `src/codex_workspace/domain` | Общие правила и модели; сохранённые модели прежнего транспорта |
| `src/codex_workspace/cli` | Единая команда `codex-workspace` |
| `src/codex_workspace/ops`, `ops/server` | Сборка релиза, установка и ресурсы служб |

API Gateway предоставляет публичный HTTPS и направляет запросы на VM.
На ноутбуке нет входящего сетевого сервиса: оба сборщика обращаются к relay
исходящими HTTPS-запросами. Relay не имеет ключей расшифровки и не запускает Codex.

## От сообщения до ответа

1. Браузер проходит Telegram-вход и получает HttpOnly cookie и CSRF-токен.
2. Доверенный браузер подписывает намерение и шифрует текст, цель и описание
   вложений ключом задачи. Relay хранит конверт и непрозрачные идентификаторы.
3. Локальный сборщик получает конверт, проверяет подпись, доверие устройства,
   срок и повторную доставку. Расшифрованный запрос записывается в локальную SQLite.
4. Перед запуском проверяются цель, SHA-256 вложений и сохранённые права задачи.
   Локальное намерение запуска сохраняется до вызова `codex exec resume`.
5. Ответ связывается с конкретным ходом. Состояния и публичные сообщения
   шифруются на ноутбуке; браузер опрашивает relay и расшифровывает их локально.
6. Push доставляется отдельным каналом; ограничения содержимого и доверия
   описаны в E2EE-документе. HTTP-шифрование Web Push само по себе не заменяет E2EE.

При desktop writer lock запрос ждёт освобождения задачи. Неопределённый результат
запуска не повторяется автоматически: сначала сверяется исходный ход.
CLI не получает инструменты `codex_app` открытого desktop-приложения.

## История и каталог

История синхронизируется независимо от исполнения: пользовательский текст
и публичные commentary/final ответы. Внутренние рассуждения и вывод инструментов
не публикуются. Каталог, история, активность, квота и диагностика передаются
через зашифрованный канал. Проверенные смещения чтения сохраняются локально.
Адаптер desktop читает явные назначения проектов. При неизвестном формате
сохраняет последний корректный снимок и сообщает об ошибке.

## Состояние и установка

Python-пакет устанавливается через `pyproject.toml`. Команды служб не зависят
от текущего каталога. `CODEX_WORKSPACE_STATE` задаёт отдельное место ключей,
очередей и контрольных точек; по умолчанию это `~/.local/state/codex-workspace`.
Для существующей установки используется её прежний каталог, без перемещения данных.
`CODEX_WORKSPACE_SOURCE` нужен командам сборки релиза, а не сборщикам.

Схема relay сохраняет совместимость хранения и миграции; наличие прежних таблиц
не означает, что работающая установка передаёт открытый текст. Открытые HTTP-обработчики каталога, сообщений, истории, вложений, квоты и
диагностики удалены. Старые адреса всегда отклоняются, даже если отметка режима
E2EE отсутствует. Без неё сессия сообщает об ошибке настройки, а сервер не
возвращается к открытому транспорту. Модели прежних записей сохраняются для
чтения и миграций, без публикации этих данных по HTTP.

`main` строго однопользовательский. `experimental/multi-user` расширяет его
участниками и локально проверяемыми правами. В Yandex Cloud развёртывается только
experimental. Подробности эксплуатации: [deployment.md](deployment.md),
[collector-routing.md](collector-routing.md), [security.md](security.md).
