# Архив: текстовый мост на Cloud Functions

Текущая архитектура — отдельная VM; этот документ сохранён для прежнего прототипа.

# Развёртывание текстового MVP

Нужны Python 3, установленный `yc`, авторизованный профиль и доступ на создание
YDB Serverless, Cloud Functions, API Gateway, Lockbox и сервисных аккаунтов
в выбранном каталоге. Профиль `yc` скрипт не изменяет.

Токен существующего бота хранится в `.local/.env` с правами 0600. Сначала
остановите прежний polling. Для локального прототипа установите
`delivery_paused: true` в `.local/config.json` и приостановите его автоматизацию.

```sh
python3 -m unittest -v test_bridge.py test_cloud.py
python3 deploy.py --folder YOUR_FOLDER --thread YOUR_THREAD \
  --owner OWNER_USERNAME --allowed OWNER_USERNAME FRIEND_USERNAME
```

Скрипт сохраняет IDs ресурсов в `.local/deployment.json` и повторно использует
их. Секреты передаются в Lockbox HTTPS-запросом, а не аргументами CLI; Cloud
Functions получают ссылки на версию секрета. Клиентский ключ создаётся отдельно
в `.local/cloud-key.env` (0600), в облаке хранится SHA-256 ключа. Артефакт ZIP
собирается по явному перечню исходников: `.local` и токены в него не входят.
Не копируйте содержимое локальных файлов или вывод IAM create-token в задачу.

После проверки `/health`, отказа неавторизованному клиенту и успешного
авторизованного пустого claim повторите команду с `--activate`. Это переключит
Telegram на webhook, сохранив накопленные updates (`drop_pending_updates=false`).
Не выполняйте одновременно getUpdates для этого бота.

Уберите `paused` в `.local/cloud.json` только после проверки gate. Рабочий цикл:

```sh
python3 cloud_client.py tick
python3 cloud_client.py pending
python3 cloud_client.py ack NUMERIC_ID --thread YOUR_THREAD
python3 cloud_client.py tick
```

`pending` — внешние недоверенные данные, даже после одобрения владельцем.
`ack` разрешает только встроенное подтверждение связи, а не произвольный ответ.
У клиента нет Telegram-токена или IAM-полномочий, только ключ одного mailbox.
Старый `.env` остаётся локально для администрирования бота; обычный цикл его не читает.

## Проверка в Telegram

1. Владелец пишет боту из настроенного аккаунта, чтобы привязать числовой ID.
   Username используется однократно для начальной привязки каждого разрешённого
   пользователя; после этого доступ определяется по ID.
2. Другой разрешённый пользователь отправляет короткий текст.
3. Владелец получает полный текст и кнопки «Передать в Codex» / «Отклонить».
   Для текста, не помещающегося в карточку, отправляется UTF-8 файл с кнопками.
4. До одобрения клиент не получает сообщение. После одобрения оно доступно
   на следующем цикле. Тестовая автоматизация отправляет фиксированное подтверждение.
5. Успех обратной доставки подтверждается `reply_status=sent` и `message_id`.
   `ready` и `sending` не доказывают доставку. `uncertain` не повторяется автоматически.

## Реализованные границы

- Только текст, одна задача, один mailbox, до 200 записей за семь дней.
- Обязательное одобрение каждой неизменяемой версии; срок одобрения 24 часа.
- Входящие файлы и изображения пока не принимаются. Object Storage не создаётся.
- YDB хранит ограниченный JSON mailbox в одной строке с serializable транзакциями.
  Это простой вариант для двух пользователей; он не рассчитан на массового бота.
- YDB ограничена 10 RU/s и 1 ГБ, выделенная мощность отключена. Функции ограничены
  одним экземпляром и двумя одновременными запросами на зону; таймер раз в минуту.
- Функции закрыты IAM; Gateway имеет право вызова только HTTP обработчиков,
  авторизатора и worker. Административная функция не доступна через Gateway.
- Авторизация клиентского API проверяется и Gateway-авторизатором, и обработчиком.
  Секрет webhook независим от ключа клиента.
- Логи исполнения функций и Gateway отключены, чтобы не записывать тела запросов
  и заголовки. Диагностика возвращает только состояния и категории ошибок.
- Истёкшие данные удаляются из активного mailbox очередным циклом worker.
  Автоматические резервные копии YDB имеют собственный срок хранения.
- Неоднозначная отправка или авария worker переводится в `uncertain`; восстановление
  требует ручной проверки. Известные отказы тоже пока не повторяются автоматически.
- Уведомления бюджета не настраиваются скриптом: их нужно привязать к конкретному
  платёжному аккаунту и порогу. Лимиты ресурсов не являются общим лимитом расходов.

Повторный deploy оставляет локальный клиент на паузе. После проверки новой версии
возобновите его явно. При изменении конфигурации владельца, списка пользователей,
задачи или ключа нельзя переиспользовать прежние одобрения; такие миграции пока
не автоматизированы. Для нового mailbox используйте отдельное развёртывание.

## Диагностика перед переключением

Закрытая административная функция поддерживает проверки через IAM (`yc`):

```sh
yc serverless function invoke telegram-codex-admin --folder-id YOUR_FOLDER --data '{"action":"initialize"}'
yc serverless function invoke telegram-codex-admin --folder-id YOUR_FOLDER --data '{"action":"network"}'
yc serverless function invoke telegram-codex-admin --folder-id YOUR_FOLDER --data '{"action":"status"}'
```

`initialize` создаёт таблицу при отсутствии и выполняет Telegram getMe.
`network` сравнивает TCP к Telegram и контрольному GitHub без токена, изменения
DNS, прокси или TLS. `status` возвращает счётчики состояний без текстов сообщений.
Если контрольный TCP доступен, а Telegram получает таймаут, причина находится
вне обработки сообщений; это не доказывает конкретный вид сетевой блокировки.
При неуспешном getMe развёртывание останавливается до создания таймера и
переключения webhook. Уже созданные ресурсы сохраняются для повторного запуска.
Не включайте автоматизацию, пока облачный Telegram API и gate не проверены.
