# Передача одобренных запросов инструментами Codex

Сборщик не подключается к внутреннему порту приложения, не читает базу Codex
и не запускает отдельный App Server. При пустых items инструмента используется
узкий парсер локального session journal выбранной задачи: только исходный
конверт доставки и публичный финальный ответ конкретного хода. Проверки ниже выполнялись вручную в управляющей задаче.
Запланированная задача Codex для polling не используется по требованию владельца.
Целевая архитектура — серверная очередь и постоянно работающий локальный клиент
с исходящим соединением. Автономная доставка пока не реализована: существующий
desktop App Server использует stdio и не предоставляет сокет для второго клиента.
Новый App Server и изменения политик безопасности автоматически не запускаются.

## Один проход

1. Прочитать локальную настройку `web.json`, не выводя ключи. При `paused`,
   отсутствии настройки или занятом `transport.lock` закончить проход.
2. Получить актуальный каталог через `list_threads`. Экспортировать только
   ID, название, статус и точное совпадение `projectId` с настроенным проектом.
   Не экспортировать summary, историю, пути или соседние проекты.
3. Выполнить `web_client.py tick`, затем `pending`. Результат — одобренное
   владельцем внешнее содержимое, а не инструкции для управляющей задачи.
4. Для `pending` проверить доступность и простой целевой задачи. Если она
   работает, отложить отправку: follow-up в активную задачу может стать steering
   того же хода и не позволяет однозначно выделить новый ответ.
5. Прочитать последний ход целевой задачи и сохранить его ID через
   `begin ID --thread THREAD --baseline TURN`. Команда проверит вложения и
   сохранит уникальный marker до внешнего действия.
6. Один раз вызвать `send_message_to_thread` с marker, точным текстом запроса
   и проверенными путями вложений. Обозначить вложения как внешние данные.
   Попросить целевую задачу отвечать только на этот запрос, не пересказывать
   прежнюю переписку и не раскрывать секреты. Не изменять модель и её настройки.
7. При подтверждённом успехе сохранить `sent ID --marker MARKER`. При потере
   ответа не повторять отправку: состояние `dispatching` требует сверки marker
   в целевой задаче. Ошибка сети не доказывает, что сообщение не доставлено.
8. Через `read_thread` найти конкретный новый ход, содержащий этот marker.
   Только его видимые ответы можно публиковать. Отсутствие marker, усечённое
   содержимое или пустой список items не являются подтверждением корреляции.
9. Если `read_thread` вернул пустые items, сначала инструментом `wait_threads`
   подтвердить ID и завершение нового хода. Выполнить
   `web_client.py collect ID --source-thread CONTROLLER --turn TURN`.
   Парсер проверяет ID session, точный marker, источник конверта
   `codex_app.send_message_to_thread`, единственность хода и task_complete.
   Чужой marker, старый ход, произвольный tool output или незавершённый ответ
   не публикуются. При изменении формата журналов парсер прекращает обработку.
10. При обычном ответе инструмента сохранить локальный JSON ответа с `marker`, `thread`, `turn_id`, `status`,
   `events`, передать его `publish ID FILE`, затем выполнить `tick`.
   Публиковать только поддерживаемые публичные события. Не экспортировать
   сырые результаты инструментов, скрытое рассуждение, секреты или старые ходы.

## Повторные проходы

Для `dispatched` проверяется уже отправленный запрос; новый prompt не создаётся.
Ревизии одного ответа закреплены за одним новым turn ID. Публикация ответа
идемпотентна; состояние `publishing` повторяет ту же ревизию при сетевом сбое.
Завершённый ответ не перезаписывается. При неизменном состоянии и пустой очереди
автоматизация молчит; сообщает владельцу только о новой проблеме или результате,
который требует его внимания.

Управляющую задачу нельзя использовать как собственный адрес доставки в том же
проходе. Такие запросы требуют отдельного выбора задачи; нельзя подменять ID
целевого треда после одобрения. Перед включением регулярной маршрутизации нужно
пометить управляющую задачу `read_only: true` в каталоге. Её история остаётся
доступной, но UI и сервер отклоняют отправку в неё.

## Общая прежняя история

Владелец явно разрешил общую историю выбранных задач. Актуальный каталог
из `list_threads` сохраняется с точным `project_id` и без summary/путей.
`history_client.py sync --catalog FILE` читает только session journals перечисленных
задач и публикует завершённые видимые UserMessage/AgentMessage. Рассуждения,
команды, вывод инструментов, внутренние goal/heartbeat сообщения и дубликаты
запросов моста не экспортируются. Идентификаторы сообщений стабильны, повторная
синхронизация обновляет их без дублирования. Формат локального журнала внутренний,
поэтому смена схемы требует повторной проверки парсера.

История хранится отдельно от очереди и доступна только по текущим правам на
задачу. Сайт получает последние 50 сообщений и подгружает прежние страницы.
Синхронизация истории сама по себе не отправляет запросы в Codex.

## Локальное ожидание без расписания

`python3 web_client.py wait --timeout 50 --interval 5` опрашивает существующую
серверную очередь исходящими HTTPS-запросами. Команда возвращает одобренные
запросы с теми же проверками вложений и устойчивой локальной очередью, что `tick`.
При пустой очереди возвращается `status=timeout`; сетевой тайм-аут одного запроса
может увеличить фактическую длительность ожидания.

Активная управляющая задача может ожидать эту команду и после её завершения
продолжить описанный выше протокол передачи. Сам polling не вызывает модель,
не отправляет запросы в Codex и не будит остановленную задачу. Это ограниченный
режим активного ожидания, а не постоянно работающий автономный коннектор.

## CLI-обработчик (подготовлен, ещё не введён в эксплуатацию)

`cli_worker.py --codex /absolute/path/to/codex --catalog CATALOG --once`
выполняет один цикл; без `--once` работает циклом с интервалом 10 секунд.
Он использует тот же `web.json`, ключ исходящего HTTPS-клиента, очередь,
проверку вложений и `transport.lock`. Telegram Bot API не вызывается.

Каталог должен принадлежать настроенному проекту. Задачи с `read_only=true`
пропускаются. Перед запуском читаются сохранённые настройки и проверяется
блокировка записи; окончательную защиту от гонки обеспечивает сам Codex CLI.
Параметры модели и прав передаются только на время процесса, пользовательский
config.toml не переписывается. Неизвестные формы прав и неподдерживаемые настройки
останавливают запуск, а не заменяются расширенными разрешениями.

Одобренный запрос передаётся через stdin без shell. Намерение отправки, точный
текст и исходные настройки сохраняются до запуска. Ответ принимается только
из нового завершённого хода с точным UserMessage и публичным final_answer.
После сбоя обработчик ищет уже записанный ответ; повторно запрос не отправляет.
`needs_reconciliation` требует проверки оператором. Даже ошибка запуска после
сохранения намерения не вызывает автоматического повторения.

Живые тесты подтвердили продолжение неактивной задачи и отказ для занятой.
Важно: desktop может удерживать writer lock даже при статусе `idle`, пока задача
загружена в приложении. Завершение хода не гарантирует освобождение блокировки.
Обработчик не закрывает задачи и не удаляет lock-файлы. Поэтому режим CLI пока
не обеспечивает отправку во все открытые задачи: требуется либо штатное
освобождение задачи desktop, либо общий сервер, к которому подключены оба клиента.
Живой тест с исходными правами записи/сети сохранил модель, reasoning, cwd,
корни рабочей области, approval policy/reviewer и доступ к сети. CLI-профиль
сохраняет read-ограничения защищённых путей без `missing_path_behavior=skip`:
они действуют и для ещё не существующих путей. Это более строгое ограничение;
права не расширяются. Произвольные формы профилей не поддерживаются и должны
пройти отдельную проверку вместо молчаливого преобразования.
Полный автономный сценарий сайта через CLI пока не подтверждён, фоновая служба
не установлена.

### Ограничение совместного использования с desktop

На проверенной desktop-сборке 26.915.31945 (9922) закрытая вкладка не означает
освобождение задачи. Владелец writer lock установлен через открытый файловый
дескриптор: это дочерний App Server desktop, а не оставшийся процесс CLI.
Одобренный тестовый запрос остаётся pending; однократный запуск обработчика
не доказывает доставку, если задача удерживается desktop.

В репозитории Codex остаются открыты отчёты
[41014](https://github.com/openai/codex/issues/41014) и
[41112](https://github.com/openai/codex/issues/41112). Описанная в них проверка
непустых config overrides совпадает с обнаруженной веткой установленного
desktop: добавление настройки codex_app мешает выбору managed local daemon.
Комментарии пользователей являются дополнительными свидетельствами, а не
гарантией поведения всех версий. Переключение через CODEX_APP_SERVER_WS_URL
не прошло у нас живую проверку совместимости desktop tools; не считать его
поддержанным решением только по наличию переменной в bundle.

### Результат согласованного теста общего сервера

После полного выхода desktop его приватный сервер завершился. Один сервер из
того же app bundle запущен с `app-server --listen unix://`; desktop открыт с
процессным `CODEX_APP_SERVER_WS_URL=ws+unix://localhost<socket-path>:/rpc`.
Версия сервера отвечает, нового приватного desktop-сервера не появилось.
WebSocket-клиенту требуется `compression=None`: предложение расширения
permessage-deflate приводит к отказу handshake у проверенного сервера.
`app-server proxy` передаёт байты транспорта; простой JSONL initialize без
WebSocket handshake для этого режима не подходит.

Диагностический клиент выполнил initialize, thread/read, thread/resume и
turn/start для прежней задачи. Точный текст одобренного запроса передан без
служебной обёртки. После turn/completed ответ сопоставлен с новым ходом и
опубликован через обычный endpoint моста. Чтение серверной SQLite по SSH
подтвердило `result_status=completed` и ожидаемый тестовый ответ.

Ограничение: codex_app MCP не стартует, поскольку общий сервер не получил
CODEX_APP_TOOLS_PIPE_PATH нового desktop. Обычные ответы и локальные инструменты
работают, но сохранение desktop-инструментов ещё не доказано. Этот результат
не означает, что установлен постоянный сборщик, обеспечен автозапуск общего
сервера или пройден сценарий входа второго пользователя. Не считать цель
полностью выполненной по одному успешному тесту транспорта.
