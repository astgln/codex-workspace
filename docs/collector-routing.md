# Доставка запросов и синхронизация истории

## Рабочие службы

Обычное desktop-приложение Codex работает независимо от двух локальных служб.
Обе обращаются к веб-серверу исходящими HTTPS-запросами. Общего App Server,
управляющей задачи и запланированных задач Codex в рабочем пути нет.

- `agent/cli_worker.py`: получает запросы из очереди, проверяет исходные права задачи,
  выполняет `codex exec resume`, сопоставляет ход и публикует ответ.
- `agent/history_watch.py`: передаёт публичную историю и наблюдения недельной квоты.
  Не отправляет запросы, не запускает Codex и не занимает writer lock задач.

Служба запросов устанавливается одной командой:

```sh
codex-workspace service install --codex /absolute/path/to/codex --catalog /absolute/path/to/catalog.json
```

Установщик отказывается перезаписывать существующую службу. Настройку
`.local/web.json` и файл клиентского ключа не выводите в терминал или отчёты.
Для службы истории используйте отдельный пользовательский launchd job с
абсолютными путями, приватными логами и перезапуском при ошибке:

```sh
codex-workspace history watch --catalog /absolute/path/to/catalog.json
```

Службы перечитывают каталог и настройку на каждом проходе; `paused` прекращает
работу. Запуск процесса проверяется через launchctl, а не только по наличию лога.

## Каталог и границы доступа

Каталог содержит идентификатор установки `project_id`, список `projects`
с точными ID и названиями и `threads` с ID, названием, статусом, `project_id`
и признаком `read_only`. Принадлежность проекту берётся из инструментов приложения,
не угадывается по cwd. Не экспортируйте retrieval summaries и локальные пути.
Перед публикацией истории весь каталог проверяется на принадлежность установке
и указанным проектам. Аккаунт видит все опубликованные проекты.

Каталог автоматически обновляется через `desktop_catalog.py`: адаптер читает
явные назначения проектов из локального состояния desktop и активные задачи
из его SQLite в режиме read-only. Пути не используются для угадывания проекта.
Это внутренний формат desktop, не публичный API; неизвестная структура
останавливает обновление, сохраняя последний проверенный снимок.
Изменение сначала публикуется на сервер, затем атомарно сохраняется в общий
каталог служб. Чтение не меняет настройки Codex.

## Состояния запроса и восстановление

Серверный запрос проходит `queued`, затем `delivered`; ответ отдельно имеет
`running`, `completed`, `failed` или `needs_input`.
Перед запуском локальный доверенный обработчик проверяет подпись, актуальные
права и неизменность запроса. Relay хранит зашифрованные записи.

Локальная очередь сохраняет намерение `dispatching` до запуска CLI, затем
`dispatched`, `publishing` и `complete`. `complete` означает подтверждённую
публикацию финального результата, а не просто exit code 0 дочернего процесса.
`worker_recovery.py` сопоставляет точный отправленный текст с единственным новым
ходом после сохранённого baseline. Marker остаётся транспортной метаданной;
текст запроса передаётся напрямую.
Вложения передаются как внешние данные с проверенными SHA-256.

Записи `dispatching`/`dispatched` сначала сверяются с журналом, никогда не
запускаются повторно автоматически. При неоднозначности результат —
`needs_reconciliation`. Не удаляйте очередь и не переводите запись вручную
в pending ради повторного запуска: исходный запрос мог уже выполниться.
Проверьте конкретный ход и его окончание; произвольный последний ответ не годится.

Для долгого запроса обработчик публикует `running` только после корреляции
нового хода; затем поддерживает свежесть сборщика. Финальный ответ сохраняет
тот же turn ID. Ошибка сети во время ожидания не запускает CLI заново.

Снимок `.local/cli-worker-status.json` содержит итог последнего прохода:

- `idle`: нет готовой работы;
- `waiting_for_tasks`: задачи заняты (`desktop_writer_lock`) либо их исходные
  настройки нельзя воспроизвести (`task_settings_unavailable`);
- `needs_reconciliation`: запуск сохранён, но завершённый ответ не установлен;
- `completed`: ответ сопоставлен; последующий tick подтверждает публикацию.

Снимок не является heartbeat во время синхронного выполнения и сам по себе
не доказывает, что процесс жив или завис. Сверяйте его с launchctl и очередью.
Не печатайте приватные stdout/stderr из `.local/cli-runs/` в общую диагностику.

Старые задачи иногда не содержат рабочих корней. Допустим только более поздний
контекст того же хода с совпадающими cwd и правами. Если его нет, продолжите
задачу обычным способом в desktop, чтобы сохранить актуальные настройки.
Не угадывайте корни и не расширяйте права для обхода ожидания.

## История и квота

`history_sync.py` используется постоянной службой и разовой командой:

```sh
codex-workspace history sync --catalog /absolute/path/to/catalog.json
```

Разовая команда выполняет один проход той же службы и использует её
зашифрованный канал и контрольные точки. При частичном результате завершается
с кодом 1. Успешные задачи публикуются даже при недоступном журнале другой задачи.
Не запускайте её одновременно с постоянной службой: они используют общий lock.

Публикуются только пользовательские сообщения и публичные commentary/final
ассистента. Внутренние рассуждения и вывод инструментов не экспортируются.
Неполная последняя строка журнала ждёт следующего прохода. Смещение сохраняется
после успешной публикации; reader/checkpoint version автоматически вызывает
идемпотентное повторное чтение после изменения интерпретации формата.
Удалять checkpoint после обновления парсера вручную не требуется.

Квота передаётся отдельным вызовом; ошибка сохраняет образец для повторной
доставки и не отменяет уже опубликованную историю. Это наблюдение из журнала,
а не прямой запрос текущего баланса аккаунта. Интерфейс показывает время
наблюдения и не выдаёт старый процент за новый после сброса окна.

## Безопасное обновление

Перед перезапуском службы запросов возьмите тот же `transport.lock`, что и
очередь, и убедитесь, что нет `dispatching`/`dispatched`. Не прерывайте активный
CLI ради обновления. SIGTERM/SIGINT запрашивает завершение после принятого
запроса; внешний force-kill всё равно может прервать процесс.
Служба истории имеет отдельный lock и идемпотентные публикации.
Обновление этих служб не требует перезапуска desktop.

Реальный запрос владельца AUTONOMOUS OK ранее прошёл через постоянную службу.
