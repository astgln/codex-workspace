# Сквозное шифрование: протокол и состояние реализации

**Статус: криптографические модули и локальная граница доверия реализованы и
проверяются отдельно. Рабочие API, сборщики и интерфейс ещё не используют их.
Сайт пока не предоставляет E2EE.** Эта документация не является заявлением
о паритете с Happy или о прохождении независимого аудита.

## Граница доверия

Доверенные стороны — локальный обработчик и явно привязанные браузеры владельца.
Сервер — хранилище непрозрачных записей и транспорт. Telegram подтверждает вход
на сайт, но не даёт ключей расшифровки и не является разрешением на исполнение
команд. Реестр устройств и обработанных запросов хранится на компьютере.
Сервер не должен иметь API для изменения этого реестра.

Идентификаторы задач, размеры, время обмена и сетевые адреса остаются метаданными.
Текст запросов, ответы, история, названия, имена и содержимое файлов, планы,
описания изменений и содержательные push-превью должны шифроваться на конечных
устройствах. Подпись автора обязательна: знание ключа чтения не должно позволять
подделать подпись локального обработчика или другого устройства.

Сайт загружает JavaScript с сервера. Взлом сервера раздачи или XSS может подменить
этот код и получить доступ к ключам и открытому тексту в браузере. Web E2EE
защищает от чтения базы и пассивного посредника, но не устраняет эту границу.
Для защиты от активной подмены клиентского кода нужен независимо доставляемый
доверенный клиент. Компрометация конечного устройства также вне этой защиты.

Эта версия не реализует double ratchet, forward secrecy или post-compromise
security. Отзыв устройства запрещает новые команды; ранее полученные ключи и
расшифрованные данные нельзя отозвать. Для прекращения чтения будущих данных
требуется ротация соответствующих ключей и доставка только оставшимся устройствам.

## Формат v1

Реализации: `workspace_crypto.py` и `web/src/crypto/envelope.ts`.
Используются WebCrypto и PyCA cryptography, собственных примитивов нет:

- AES-256-GCM, 128-битный тег, случайный 96-битный nonce;
- новый 256-битный salt на каждую запись, HKDF-SHA-256 выводит ключ записи;
- ECDSA P-256 / SHA-256 подписывает контекст, salt, nonce и шифротекст;
- открытый ключ подписи — канонический DER SPKI, fingerprint — SHA-256 SPKI;
- подпись в проводном формате — 64 байта `r || s`, как в WebCrypto;
- бинарные поля — base64url без padding; неканонические варианты запрещены.

Конверт имеет **ровно** поля `v`, `context`, `key_id`, `signer`, `salt`, `nonce`,
`ciphertext`, `signature`. Дополнительные поля и неизвестные версии запрещены.
`context` — массив `[workspace, scope, kind, record, revision]`. Четыре строки
содержат от 1 до 512 байт корректного UTF-8, revision — целое от 1 до 2^53−1.
Kind — один из `request`, `response`, `history`, `catalog`, `attachment`, `push`,
`key-wrap`. Для задач scope — ID задачи. Серверные ID очереди не определяют
идентичность команды: record для запроса — случайные 256 бит, выбранные клиентом.

Во всех бинарных подписываемых структурах используется `frame(parts...)`:
каждая часть предваряется её 32-битной длиной в big-endian. JSON не участвует
в канонизации подписи. Domain — UTF-8 `codex-workspace/e2ee/v1`.

```
key_id = base64url(SHA256(frame(domain, "key-id", scope_key)))
aad = frame(domain, "envelope", workspace, scope, kind, record,
            decimal(revision), key_id, signer)
content_key = HKDF-SHA256(scope_key, salt,
                         info=frame(domain, "content-key", aad), length=32)
ciphertext = AES-256-GCM(content_key, nonce, plaintext, aad)  # включает тег
signature = ECDSA-SHA256(frame(domain, "signature", aad, salt, nonce, ciphertext))
```

Получатель передаёт ожидаемый контекст и заранее доверенный открытый ключ,
а не берёт доверие из полей конверта. Проверяются версия, контекст, key_id,
fingerprint и подпись; только затем выполняется расшифровка. Максимум открытого
содержимого одного конверта — 6 MiB. HTTP и файловые лимиты интеграции должны
учитывать base64 и накладные расходы. Автоматического перехода к plaintext нет.

## Запросы и повторы

`request_intent.py` проверяет расшифрованное намерение: точные поля версии,
workspace, задачи и request_id, время создания/истечения, текст и вложения.
Запрос действует не более суток, допускается до 60 секунд опережения часов.
Повторяющиеся JSON-ключи, невалидный UTF-8, лишние поля, дубликаты вложений,
пути вместо имён и некорректные хеши отклоняются. Вложение связывает ID, имя,
размер и хеши открытого содержимого и шифротекста.

`device_trust.py` хранит доверенные SPKI и журнал принятых request_id в локальной
SQLite с правами 0600 в каталоге 0700. Проверка ключа, подписи, срока и запись
nonce выполняются под `BEGIN IMMEDIATE`. Повторный nonce запрещён даже при новом
ID очереди, шифротексте или целевой задаче. Отозванный fingerprint нельзя
восстановить повторной регистрацией; требуется новый ключ устройства.

Это **не** готовая exactly-once интеграция с CLI. Потребитель обязан связать
принятие намерения с существующей долговечной очередью исполнения. Если nonce
уже принят, а подтверждённого результата нет, нельзя автоматически запускать
команду снова. Потеря локальной базы защиты от повторов должна требовать нового
эпохального набора ключей/устройств, а не восстанавливать доверие от сервера.
Права выбранной задачи Codex и проверка локального каталога сохраняются.

## Привязка устройства

Предусмотрена согласованная схема: QR/ссылка с доверенного устройства и отдельный
ключ восстановления. Пока реализованы функции протокола, **не экран настройки**.

Локальная сторона создаёт приглашение: случайные ID и 256-битный секрет,
workspace, закреплённый открытый ключ локального подписанта, срок 10 минут.
Приглашение не публикуется через сервер. Ссылка помещает эти данные в URL fragment,
не в query/path. Интерфейс обязан убрать fragment из адресной строки до загрузки
данных, не писать его в логи и не отправлять через push или аналитику.
QR/ссылка — краткоживущий bearer-секрет: получивший его может привязать устройство.

Новое устройство создаёт собственный ключ подписи, шифрует фиксированное
доказательство `codex-workspace/device-pairing/v1` секретом приглашения и подписывает
его своим ключом. Контекст: `scope=devices`, `kind=key-wrap`, `record=invitation_id`,
`revision=1`. Открытый SPKI передаётся вместе с доказательством. Здесь доверие
появляется из владения секретом приглашения, а не из присланного SPKI.

Локальная сторона атомарно принимает только одно устройство на приглашение,
добавляет ключ в реестр и возвращает подписанный зашифрованный набор ключей
с revision=2. Подписант закреплён в приглашении. Повтор точного offer возвращает
тот же шифротекст в пределах срока; другой offer отклоняется. Секрет удаляется
из активной строки локального реестра. Браузер проверяет подпись по QR-пину.
Перед сохранением потребитель обязан проверить схему набора ключей, fingerprint
получателя и область действия. Установки частично проверенного набора быть не должно.

Код восстановления: `cw1_` + base64url(32 случайных байта + 4 байта checksum).
Checksum — первые четыре байта SHA256(frame(domain, "recovery", seed)).
Ключ обёртки — HKDF-SHA256(seed, salt=empty,
info=frame(domain, "recovery-key"), length=32). Это не пароль и не ключ Telegram.
Реализованы генерация, проверка опечатки и вывод ключа. Зашифрованный recovery
пакет, его формат, экран сохранения/восстановления и политика ротации ещё нужны.

## Условия включения

До переключения рабочего сервиса должны быть завершены:

1. Локальное хранилище ключей, браузерное хранилище, QR/ссылка, recovery-пакет,
   отзыв устройства и ротация, включая подтверждённое восстановление на новом браузере.
2. Непрозрачные серверные API и строгая версия режима без plaintext fallback;
   шифрование всех перечисленных каналов, а не только POST сообщений.
3. Проверка signed intent и вложений перед CLI, атомарная связь с локальной
   очередью и сохранение ограничений выполнения задач.
4. Шифрованные push с расшифровкой в service worker. При отсутствии ключа —
   нейтральное уведомление. Проверка iOS PWA обязательна отдельно от браузерных тестов.
5. Миграция прежних записей через доверенный компьютер: полная проверка
   расшифровки и количества записей до удаления plaintext. Учитываются SQLite,
   WAL, uploads, previews, снимки и резервные копии; шифрование новых данных
   не делает старые копии секретными задним числом.
6. Проверка захвата дампа сервера, подмены ключей/задачи/автора, replay, потери
   устройства, истечения приглашения и восстановления после сбоя.

Действующие службы сейчас не переключаются. При включённом E2EE дальнейшее
отсутствие ключей или повреждение конверта должно блокировать операцию; нельзя
молча отправлять открытый текст или использовать доверие, присланное сервером.

## Проверки

```
python3 -m venv .local/crypto-venv
.local/crypto-venv/bin/python -m pip install -r crypto-requirements.txt
.local/crypto-venv/bin/python -m unittest test_workspace_crypto test_device_trust test_request_intent
cd web
npx playwright test tests/crypto.spec.ts tests/pairing.spec.ts
```

`CRYPTO_TEST_PYTHON` позволяет выбрать интерпретатор для двусторонних фикстур.
Фикстуры генерируют только одноразовые тестовые ключи, не читают рабочие секреты.
Проверки протокола не доказывают, что рабочий трафик уже шифруется.

Источники: [W3C WebCrypto](https://www.w3.org/TR/webcrypto/),
[PyCA AEAD](https://cryptography.io/en/latest/hazmat/primitives/aead/),
[PyCA changelog](https://cryptography.io/en/latest/changelog/).
