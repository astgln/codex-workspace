# Границы доверия и проверки безопасности

Вход разрешён только устройствам из подписанного локальным обработчиком реестра.
Сервер проверяет ECDSA-подпись одноразового challenge с привязкой к origin и
пространству. Открытый корневой ключ закрепляется при SSH-установке; транспортный
ключ не позволяет добавлять устройства. Подробности — [вход по ключу](device-login.md).

Cookie `__Host-workspace-session`: Secure, HttpOnly, SameSite=Lax, Path=/.
В базе хранится хеш случайного идентификатора. Изменяющие запросы требуют точного
Origin и CSRF. Секрет сессии не передаётся JavaScript и не хранится в localStorage.
Ключ локальной службы отделён от браузерной авторизации и обладает доступом
к синхронизации. Секреты хранятся вне Git: локальные файлы с закрытыми правами,
закрытый серверный config; значения не выводятся в диагностику.


Браузер получает непрозрачную Secure/HttpOnly-сессию. Изменяющие запросы
требуют точный Origin и CSRF-токен. Выход отзывает сессию. Browser cookie
не даёт права вызывать API локального сборщика, и наоборот.

Права проверяются сервером при чтении истории, отправке сообщений и доступе
к вложениям. Владелец отправляет свои запросы без отдельного подтверждения;
для участника необходимость одобрения определяется политикой, выбранной
владельцем. Когда одобрение требуется, оно относится к конкретному снимку
текста, задачи и файлов. Запрет отдельной задачи сильнее разрешения проекта.

## Очередь и отзыв доступа

Перед каждым новым запуском локальный `Queue.begin` вызывает закрытый
`/v2/inbox/validate`: проверяются идентификатор, задача, снимок, срок одобрения,
текущие права отправителя и отсутствие режима «только чтение».
Недоступность сервера, ошибка или неоднозначный ответ не разрешают запуск.
В действующей архитектуре эта проверка обязательна перед CLI-запуском.
Она не повторяет ранее начатые запросы.

В варианте Yandex VM принимает SSH только с административного /32, приложение —
от сети Gateway. В Compose relay опубликован только на loopback сервера; внешний
HTTPS обслуживает reverse proxy. Relay работает без root и capabilities, с
read-only корневой ФС и отдельным volume. Локальный компьютер делает только
исходящие HTTPS-запросы.
Настройки VPN, TLS и корпоративной безопасности приложение не изменяет.

## Границы этой защиты и требования СИБ

Отсутствие входящих портов не отменяет удалённое управление: серверная очередь
передаёт задания процессу на компьютере, который запускает Codex с правами
выбранной задачи. Получатель запроса, TLS и вход по ключу не являются
подтверждением допустимости такого канала по корпоративной политике.

По решению владельца синхронизируются все проекты, без списка исключений.
При включённом E2EE переписка, названия и содержимое файлов передаются в облако
зашифрованными; ключи остаются на доверенных конечных устройствах. Серверная сессия
сама по себе не даёт ключей или права исполнения. При этом сервер раздаёт код
веб-клиента: его активная подмена может раскрыть браузерные ключи и данные.
Компрометация доверенного устройства также остаётся угрозой. Исходящие соединения
не устраняют эти риски; подробная граница защиты описана в [E2EE](e2ee.md).

Публичные ответы и история проходят один фильтр распознаваемых секретов до
передачи с компьютера. Он скрывает типовые токены, приватные ключи, пароли в
настройках и заголовки Authorization, но не определяет коммерческую тайну,
персональные данные или произвольные секреты. Пользовательские загрузки и
запросы не считаются автоматически очищенными. Старые данные и резервные копии
могут содержать ранее переданную информацию. Это не корпоративная DLP.

Для признания схемы допустимой СИБ нужны правила организации о внешнем хранении
данных и удалённом управлении, учёт доверенных устройств и разрешённый способ
доступа. Эти организационные условия невозможно установить по исходному коду.
Без соответствующего согласования нельзя называть данную личную установку
безопасным корпоративным решением; альтернатива — отдельное разрешённое устройство
и разрешённая среда хранения. Приложение не меняет VPN или средства контроля.

## Проверенные технические меры

- Ключ сборщика не позволяет подделывать подписанный реестр устройств.
- Одноразовый переход доверия отзывает прежние cookie-сессии и push-регистрации.
- Анонимный вход ограничен бюджетом запросов до криптографической проверки;
  лимит не доверяет подделываемому X-Forwarded-For.
- Ответы API, в том числе ошибки и восстановление сессии, получают no-store,
  nosniff, запрет embedding, no-referrer и HSTS.
- Клиент не следует перенаправлениям, не принимает произвольные API URL и
  ограничивает размер читаемого ответа. Локальная очередь создаётся с правами 0600.
- Тесты проверяют отказ при подмене ключей, отзыв сессий, фильтрацию секретов
  до сетевой отправки и сохранение исходных ограничений выполнения Codex.

Рекомендации для оценки: [CISA: securing remote access software](https://www.cisa.gov/resources-tools/resources/guide-securing-remote-access-software),
[OWASP: session management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html).
Проверка исходников и зависимостей не заменяет внешний penetration test и решение СИБ.

Отзыв доступа блокирует ещё не отправленный в Codex запрос, даже если он
уже скачан на ноутбук. Скачивание его вложений также прекращается. Проверка
прав не может отменить уже начатый ход: между серверной проверкой и локальным
вызовом существует короткое окно, а отмена выполняющейся задачи требует
отдельного действия в Codex.

Одобрение не создаёт новую песочницу: запрос выполняется с правами выбранной
задачи. Ключ сборщика и аккаунт владельца — привилегированные границы доверия.
Файлы проверяются по SHA-256 перед запуском и передаются как данные;
сборщик не исполняет их. Защита от повторной отправки опирается на сохранённое
намерение и идентификатор хода, а не на повтор после таймаута.

## Защита VM

Веб-служба работает от отдельного непривилегированного пользователя,
без capabilities, с NoNewPrivileges, ProtectSystem=strict и ProtectHome.
Каталог состояния имеет режим 0700, SQLite — 0600; StateDirectoryMode
не позволяет systemd вернуть каталогу публичный режим при перезапуске.
Конфигурация с секретами доступна только root и группе службы (0640).

Порт приложения принимает соединения только из диапазона API Gateway;
SSH ограничен настроенным адресом /32. Локальный сборщик использует исходящий
HTTPS. Настройки TLS, VPN и безопасности Codex не ослабляются.

## Проверка изменений

- Серверные тесты проверяют подписи, replay, сессии, Origin/CSRF, разделение
  ролей и ключей, отзыв прав после скачивания, срок одобрения, неизменность
  запроса и вложений, неизвестные критические расширения JWT.
- Тесты действующего CLI-обработчика подтверждают отсутствие запуска при отказе
  сервера, неверном формате ответа и сетевой ошибке.
- На VM проверяются эффективные параметры systemd, режимы файлов и отказ
  постороннему системному пользователю в чтении SQLite.
- `npm audit --omit=dev` проверяет рабочие зависимости интерфейса; фактически
  установленные Python-пакеты сверяются с advisories PyPI. Нулевой результат
  означает отсутствие известных записей на момент проверки, не отсутствие
  любых уязвимостей. Установщик обновляет свой pip до закреплённой версии;
  версии библиотек входа закреплены в requirements.

Первичный источник одного из устранённых дефектов зависимости:
[PyJWT: неизвестные критические заголовки](https://github.com/jpadilla/pyjwt/security/advisories/GHSA-752w-5fwx-jx9f).

Проверки не заменяют независимый пентест, проверку реального аккаунта второго
участника. Действующий автономный CLI не использует desktop-инструменты
`codex_app`; их поддержка не является свойством этой архитектуры.

## E2EE


Криптографический протокол и локальный реестр устройств описаны в [E2EE](e2ee.md).
Действующая установка была переключена на обязательный E2EE с чистым запуском,
по явному отказу владельца от переноса старых веб-данных. Локальная история
публикуется зашифрованной. Это не гарантирует удаления сторонних облачных снимков
и не подтверждает непроверенные сценарии восстановления или iOS push.
Фактический режим конкретной установки проверяйте по её pins и работающим службам.
